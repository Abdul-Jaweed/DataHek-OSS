Stage 02–03 · The Planner

The planner thinks, the validator decides

The planner is an LLM with a strict contract: return JSON for the LogicalPlan — nothing else. The engine never trusts the model; every plan is validated against the real schema.

PROMPT Schema-aware context LLM

question + schema summary
+ target dialect (postgres → allowed functions)
+ skills / custom prompt templates
+ feedback loop on invalid attempts

VALIDATE Typed checks deterministic

source ∈ tables
column ∈ schema columns
aggregate fn ∈ dialect allowlist
group_by ⊆ select · read-only only

attempt 1 → "uniq(event_id)" on postgres ✗ PLAN_INVALID
feedback → "aggregate function 'uniq' is not supported on dialect 'postgres'. Fix the plan."
attempt 2 → "count_distinct(event_id)" ✓ VALID
# max 2 retries, then a clarifying question instead of guessing
Stage 04 · The Guardrail Pipeline

Typed decisions, not if-statements

The middleware pipeline evaluates the request and returns one typed decision. Everything downstream — audit, masking, approval — reacts to that decision.

Is the plan read-only?ALLOW
Does it contain a WriteNode / DELETE / DROP?DENY
Does it touch sensitive columns (PII tags)?MASK
Entitlement limits exceeded (connections ≤ 5, prompts ≤ 3)?RATE_LIMIT
Query complexity / timeout bounds exceeded?DENY

Every decision is recorded to the audit trail with actor, tenant, plan sources and policy version — including refusals. The same pipeline guards API, CLI, UI and MCP; MCP is never a privileged bypass.

Stage 05–06 · Execute → Mask

Compile once, execute safely, mask before reasoning

COMPILE LogicalPlan → dialect SQL per provider

ReadNode{traces, service, count(*) }
  → SELECT service, count(*) AS n
    FROM traces WHERE status = 'error'
    GROUP BY service ORDER BY n DESC
# the same plan compiles for 4 dialects

MASK Before the model sees data privacy

Sensitive columns (schema tags) are masked in the result set before the explanation model receives it — the answer generator never sees raw PII, and the row data sent to the client is redacted too.

Connection secrets

settings may be secret://infisical/… — resolved once, before schema discovery, never logged.

Query errors

driver errors mapped to typed codes: QUERY_FAILED vs CONNECTION_FAILED — honest 422s, not 502s.

Audit

who asked · which connection · which SQL · which policy version · what came back.

Design principles

Why it's built this way

01 Read-only by construction

Write plans are structurally impossible to execute — denied at the plan layer before any SQL is generated.

02 Trust nothing, verify

The LLM proposes; deterministic validation, dialect allowlists and typed decisions dispose.

03 One pipeline everywhere

UI, API, CLI and MCP share RequestContext → guardrails → audit. MCP is never a bypass.

04 Contracts, not forks

Providers, stores and secrets are contract-bound — Enterprise swaps implementations, never the engine.

05 Progress is UX

Real-time pipeline stages + streaming tokens keep users oriented instead of staring at spinners.

06 Audit everything

Every decision — including refusals — is recorded with actor, tenant, plan and policy version.
