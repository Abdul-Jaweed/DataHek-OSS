Why a Context Layer

Before

  • Schema dumped into every prompt
  • No notion of trust or freshness
  • LLM guesses semantics (encodings, grains)
  • Enterprise policy bolted onto prompts
  • No review, no versioning, no audit

With the Context Layer

  • Bounded, relevant slices per question
  • Provenance + trust on every artifact
  • Semantics derived, proposed, then human-validated
  • Governance travels with context, enforced by the engine
  • Immutable versions, full audit trail
Persistent Context → Retrieval → Selection → Composition → Compilation → Context Package → Agent → LLM

Context artifacts

ArtifactContentsProvenance
Schematables, columns, types, PK/FK, indexesDatabase
Profilenull ratio, distinct, uniqueness, min/max/avg, rolesDatabase
TopologyFK + inferred edges, cardinality, join pathsDB / inferred
Granularity"1 row of X means …" grain statementsSystem
TaxonomyDimension / Measure / Identifier / Temporal hierarchySystem
Ontologyconcepts, synonyms, controlled relationshipsLLM (PENDING)
Governancesensitive/restricted columns, allowed operationsSystem
Quality / Freshnesscoverage scores, staleness signalsSystem

Every artifact carries an envelope: kind, version, provenance, trust, validation status, confidence. Sensitive columns are counts-only — no raw values, ever.

Build sequencing — 9 ordered stages

INTROSPECT ─► PROFILE ─► TOPOLOGY ─► GRANULARITY ─► TAXONOMY ─► ENRICH ─► GRAPH_BUILD ─► QUALITY ─► PUBLISH

Fixed order

Later stages consume earlier artifacts: topology needs schema, taxonomy needs profiles, enrichment needs taxonomy, the graph needs everything.

Retry + degrade

Each stage retries once; failures degrade with a warning and the build still publishes a lower-quality record.

Enrichment is opt-in

The only LLM stage — spends tokens, so it is off by default; proposals arrive PENDING, never authoritative.

Skip if current

A build whose schema hash matches the active record is skipped; graph rebuilds MERGE by stable ids and prune.

Live (InsForge, 40 cols / 730k rows): ~29 s total, PROFILE ≈ 27 s (exact distinct counts dominate).

Lifecycle & versioning

BUILDING ─► ACTIVE ─► SUPERSEDED
                │  └─► STALE ─► (rebuild) ─► ACTIVE (v+1)
                └─► INVALIDATED
  • Versions are monotonic per (org, connection, scope); ACTIVE versions are immutable.
  • supersedes chains versions; history stays readable forever.
  • Invalidation on schema-hash mismatch, permission change, manual request, or staleness.
  • Retrieval surfaces stale=true; stale governance is never served.

Retrieval — deterministic selection

  • Tokenize: lowercase, split snake_case (error_category → error, category), drop stopwords
  • Score tables: name ×3, column match +2, metric/ontology/taxonomy boosts
  • Pull one-hop join neighbours
  • Caps: 8 tables, 40 columns; no-match floor in schema order
  • Filter profiles, grain, taxonomy, ontology to selected tables; topology to edges between them; metrics by overlap
  • Governance always included in full
  • stale=true when the schema hash moved

Bounded by construction

A hostile "select everything" question still returns a capped slice. No LLM, no embeddings, no whole-store dumps — reproducible for the same question and record.

Live p50: 36.5 ms including parallel artifact reads.

Composition — budget with ordered degradation

Mandatory

  • schema
  • governance
  • granularity

If these alone exceed the budget → insufficient_reason="budget". They are never dropped.

Optional — drop order

profiles → taxonomy → topology → ontology → metrics

Metrics are relevance-pruned before being dropped wholesale. Cost model: len(str(section)) // 4 — deterministic and monotonic.

Compilation — deterministic packages

  • Byte-identical for the same inputs — replayable and diffable.
  • Semantics summary: dimensions/identifiers/temporal from taxonomy; profile roles as fallback; metrics carried through.
  • Trust floor: minimum effective trust of included content — an included LLM ontology lowers the package to PROPOSED.
  • Governance: composed block, or synthesized SYSTEM governance (SELECT only) for OSS local.
  • Degradation: dropped sections recorded in budget.dropped_sections and degraded.
  • Fail closed: insufficient composition overrides quality to INSUFFICIENT with the reason.

Planner integration & degradation matrix

With a package the planner renders schema + grain + joins + restricted columns + metrics and skips the live catalog. Without one, the pre-context path runs unchanged.

Human validation loop

build ─► PENDING items ─► GET /context/pending ─► approve | edit | reject
              │                                          │
              │                                          ▼
              └──── fixed priors ◄──── new version (HUMAN_VALIDATED)
  • Reviewable: ontology concepts/relationships, taxonomy nodes, grain statements.
  • Edits are whitelisted; rejections stay traceable to their origin.
  • Validated items are fed back as "already validated — do not re-propose".
  • Humans are never asked the same question twice.

Schema Knowledge Graph

  • Projects schema, profiles, topology, grain, taxonomy, metrics, ontology into a property graph — stable ids, vocabulary-only edges, version/provenance stamps.
  • Idempotent rebuilds: MERGE by id, prune stale nodes per connection.
  • Backends: Neo4j (optional [graph] extra + compose profile) and an in-memory adapter passing the same contract suite.
  • Every read tenant-scoped and depth-bounded; Cypher confined to the adapter.

Security & tenancy

  • Credentials never enter artifacts (verified with a password-bearing build).
  • Sensitive columns: counts only; taxonomy excludes them.
  • Every read scoped by org_id at the storage layer.
  • Cross-tenant retrieval/validation returns nothing / NOT_FOUND.
  • LLM content is PROPOSED/PENDING; it can never raise the trust floor.
  • Injected text reaches prompts only as data — never the system prompt.
  • Encoded columns without documented semantics → clarification (fail closed).
  • RLS filters (Enterprise) are applied in the engine and stored in checkpoints.

Known limitations & future work

Limitations

  • Value hints in profiles (deferred): encoded columns clarify instead of guessing
  • No window functions or self-joins in plans
  • Profiling cost scales with width (exact distinct counts)
  • Upstream model latency dominates end-to-end time

Next

  • Low-cardinality value hints (non-sensitive) into profiles
  • Approximate distinct counts for very wide tables
  • REST/UI review inbox for the validation queue
  • Enterprise policy/RLS refinements layered on the same contracts
