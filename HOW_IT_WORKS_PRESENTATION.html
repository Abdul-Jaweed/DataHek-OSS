Step 1 of 20

You send the question.

Behind the scenes

The web app sends one request to the API:

POST /ask/stream
{ question: "How many traces are there?",
  connection_id: "ch1" }

You see

An empty answer bubble appears with a blinking cursor.

Nothing has run yet.

Step 2 of 20

The server checks who you are.

Behind the scenes

If DATAHEK_AUTH_MODE=local, your API key or login token is validated and your roles are attached to the request.

With auth off, this step is skipped entirely.

You see

Nothing — this takes milliseconds.

If the key were missing or wrong, you'd get 401 here.

Step 3 of 20

INPUT GUARDRAIL — your question is scanned.

Behind the scenes

The guardrail checks three things:

• length (max 2000 characters)
• control characters
• injection / write-intent signatures — "ignore previous instructions", DROP TABLE, DELETE FROM…

Your question is normal → it passes. Injected questions are refused before the AI is called.

You see

The progress bar starts:

Connecting…
Step 4 of 20

Is this a complex question?

Behind the scenes

A quick heuristic looks for comparatives, trends, or very long questions.

Simple → go straight ahead. Complex → the analyst AI splits it into 2–4 sub-questions, each running through this exact flow.

You see

Nothing extra — simple questions cost no extra AI calls.

Step 5 of 20

The planner prompt is assembled.

Behind the scenes

The prompt contains:

• the schema — tables + columns (capped at 15 tables / 12 columns each)
• the database type and its allowed functions
• your metric definitions (semantic layer)
• the last few conversation turns
• any skills or custom prompt template

You see

Planning a validated query…
Step 6 of 20

AI CALL #1 — the AI proposes a plan (not SQL).

Behind the scenes

The AI answers with a small structured plan:

read "traces"
count(*) → alias "total_traces"

It never writes raw SQL and never touches the database.

You see

Still Planning…

This is the slow step (~10 seconds) — the first AI call.

Step 7 of 20

The plan is validated against the real schema.

Behind the scenes

Pure code (no AI) checks:

• do the tables exist?
• do the columns exist — including dotted table.column refs and join conditions?
• is the function allowed on this database type?
• is the plan read-only?
• is the GROUP BY consistent?

You see

Still Planning… — this check is instant.

Step 8 of 20

Invalid plans get one retry — then a clarification.

Behind the scenes

If validation fails, the exact reason goes back to the AI (e.g. "uniq is not supported on postgres") for one more attempt.

Still invalid → the engine asks you to clarify. Nothing unvalidated ever executes.

You see

Either the flow continues, or you get a clarifying question — never a wrong query.

Step 9 of 20

GUARDRAIL PIPELINE — four deterministic guards.

Behind the scenes

1 · Rate limit — 120 requests/minute per user
2 · Policy — allowlists · sensitive tables · large exports
3 · Read-only — write plans are structurally impossible
4 · Complexity — row limit capped to the provider maximum

They run in order; the first non-ALLOW wins.

You see

Executing validated query…
Step 10 of 20

Sensitive or huge query? A human decides.

Behind the scenes

If policy says REQUIRE_APPROVAL, the API answers 202 with an approval id — nothing runs yet.

Someone clicks Approve in the Approvals page. You ask again with the id → the one-shot grant is consumed → execution continues. Reject → 422, audited.

You see

A pending item in the Approvals inbox instead of an answer.

Not triggered in this example — normal queries skip it.

Step 11 of 20

The decision is recorded.

Behind the scenes

The guardrail decision (ALLOW / DENY / REQUIRE_APPROVAL / RATE_LIMIT) is written to the audit trail with you, the tenant, the plan's tables and the policy version.

Refusals are audited too — accountability works both ways.

You see

Nothing — the trail is for operators and auditors.

Step 12 of 20

Secrets are resolved, then the plan becomes SQL.

Behind the scenes

Connection credentials stored as secret:// references are resolved (e.g. from Infisical) — they were never part of the plan or the AI's context.

Then the plan compiles to real SQL:

SELECT count(*) AS total_traces
FROM traces
LIMIT 10

You see

Nothing — you get the answer, not the SQL.

Step 13 of 20

The database connection opens READ-ONLY — physically.

Behind the scenes

Each connector locks writes at the database level:

• Postgres — read-only transactions
• SQLite — file opened with mode=ro
• MySQL — read-only session
• ClickHouse — readonly=1

Even a perfect attack at this point cannot write.

You see

Nothing — but this is the layer that can never be argued with.

Step 14 of 20

The query executes.

Behind the scenes

The database returns the rows — here, one number: 8.

Errors stay honest: bad SQL → QUERY_FAILED (422); unreachable database → CONNECTION_FAILED (502).

You see

Generating answer…
Step 15 of 20

Sensitive columns are masked.

Behind the scenes

Columns tagged as sensitive are masked in the result before anyone reasons over them — the AI included.

You see

Nothing in this example — no sensitive columns were touched.

Step 16 of 20

The run is checkpointed and audited.

Behind the scenes

A checkpoint saves your question, the plan, the compiled SQL and the row count — replayable later with no AI involved.

The execution is added to the audit trail.

You see

Nothing — but this is why you can inspect or replay any past run.

Step 17 of 20

AI CALL #2 — the answer is written and streams in.

Behind the scenes

The reasoner AI receives the question and the (masked) result and writes plain language:

"There are 8 traces in total."

If the model were down, a deterministic summary is used — the request never fails.

You see

Words appear one after another with a blinking cursor.

Step 18 of 20

OUTPUT GUARDRAIL — the answer is scanned.

Behind the scenes

Every chunk is scanned for leaked secrets and personal data:

emails · phones · card numbers · SSNs · API keys · bearer tokens · passwords · connection strings

Found → replaced with a label and recorded in the audit trail.

You see

If anything was redacted: a ⚠ redacted: … line under the answer.

Step 19 of 20

AI CALL #3 — an independent verification.

Behind the scenes

The verifier sees only your question and the result — never the planner's reasoning — so it can't inherit its mistakes.

ok — "a count of 8 directly answers the question"

You see

A small ✓ verified line under the answer.

Step 20 of 20

Delivery — and the conversation is saved.

Behind the scenes

The answer, the results table and the turn are persisted — so follow-ups like "and per service?" resolve against this turn.

You see

The answer + table (total_traces = 8) + Chart / CSV buttons.

Total for this example: ~15 seconds, 3 AI calls.

Guardrails · INPUT side

Everything that comes IN is checked — whoever sends it.

ActorInput guardrail
User (web · API · CLI)injection & write-intent signatures · max length · control characters — before any AI call
AI (planner prompt)sees only the schema summary, your question and prior turns — never credentials; injection in data can't change decisions because deterministic code decides
MCP clientsMCP requests produce the same RequestContext → guardrails → audit pipeline as the API — MCP is never a bypass
Tools (MCP tools)tool parameters validated (connection must exist, names bounded) · tool execution runs through the same masking and read-only enforcement
Database (queries)plan validated (tables · columns · joins · dialect) · write plans structurally impossible · connection physically read-only
Guardrails · OUTPUT side

Everything that goes OUT is checked too.

ActorOutput guardrail
AI plan (output 1 of 3)validated against the real schema before execution · invalid → retry → clarification · never runs unvalidated
AI answer (output 2 of 3)scanned chunk by chunk — emails · phones · cards · SSNs · API keys · bearer tokens · passwords · connection strings → redacted + audited
AI verification (output 3 of 3)independent verdict shown as ✓ / ⚠ · the writer's reasoning is never shared with the checker
MCP tool resultstyped results · credentials never present · error messages scrubbed (no secrets in errors) · same redaction rules as the API
Rows to the usersensitive columns masked before reasoning and before display — the AI never sees raw PII
Everythingevery decision (allow · deny · redact · approval · rate) written to the immutable audit trail
